Six agents that run an MLOps pipeline on their own

Each agent watches one part of the pipeline, measures it with models, decides with an LLM, and acts through code. They talk to each other directly, trace failures back to their source, and ask a person only before production changes.

Advanced Data Science Project, Topic 4: Multi-Agent DevOps / MLOps Pipeline. ESPRIT, class 5DS, 2026/2027. Ten weeks, a team of five, Design Thinking method.

Overview

The pipeline runs in order from code to live model. One agent sits on each stage. All six share a message board, a memory of past incidents and a sandbox for safe tests.

Stages run left to right. Agents do not: they run at the same time and talk through the board whenever something happens.

AgentWatchesThe question it answers
BuilderThe repositoryHow do I turn this code into a working pipeline?
ReviewerCommits, pull requests, CIIs this change safe, and was it intended?
InspectorIncoming dataPass, repair or quarantine this batch?
TrainerTraining runs, model registryIs retraining worth it? Is the new model better for everyone?
DeployerServing, traffic, resourcesMore traffic, hold or roll back? Enough capacity?
MonitorLive predictionsIs the model really getting worse, and why?

Why there is no coordinator agent

A coordinator's usual jobs are either simple rules or already belong to an agent, so it would fail the project's own test: could a script do it?

Coordinator jobHandled instead by
Group related alertsA rule: same lineage branch and same time window
Settle conflictsTwo fixed rules (see communication)
Check a fix workedThe acting agent verifies its own action
Find the root causeAgents question each other along the lineage map; the one closest to the source claims the incident

The LLM must answer in a fixed JSON format and may only pick from its agent's action menu:

{
  "action": "quarantine",
  "level": 1,
  "reason": "fare_amount median is 100x higher than usual; matches past incident 'cents instead of dollars'",
  "confidence": 0.86,
  "success_check": "next batch passes schema checks"
}

Action levels

  1. 1
    Just do it

    Safe and reversible. Stop a failing run, quarantine a batch, run extra tests.

  2. 2
    Test, do, tell

    Must pass in the sandbox first. Repair data, retrain, move the canary to 5% or 25%.

  3. 3
    Ask a person

    Anything production users see. Promote to 100%, a code and model migration.

  4. 4
    Never

    In no menu. Delete data or models.

One exception: the Deployer may roll back without asking when errors cross a hard limit, because it only restores a version a person already approved.

Files it generates from templates

Makefile (install, data, train, evaluate, serve, test, all), Dockerfile, docker-compose.yml (current and candidate serving containers, router, MLflow, board), the GitHub Actions workflow, MLflow config, a first Pandera schema.py for the Inspector, and agents.yaml with each agent's paths and subscriptions.

How they communicate

Not sequential: every agent runs at the same time

The pipeline's stages happen in order, but the agents don't take turns. Each one runs its own loop in its own process. Messages are posted on events, like emails to a shared inbox: the sender keeps working and the receivers pick them up on their next check. Only inside one conversation, such as a question and its answer, does order matter.

  • models watching
  • LLM awake
  • sandbox job
  • message

One stretch of time. The Trainer keeps training while the Monitor and Inspector sort out a data question, and the Deployer holds a rollout the moment it's asked to.

TypeMeaningExample
Finding"I noticed X." An answer is a Finding that replies to a Question.Monitor: estimated accuracy down 6% on airport trips

How the board is built

Storage

A single messages table in SQLite or Postgres. Agents poll it every few seconds for rows addressed to them. It's simple, easy to debug, and every row is already an experiment log entry. If polling becomes a bottleneck, move to Redis Streams with one consumer group per agent and the same schema.

Topics

Each message has a topic from the lineage map, such as feature:trip_distance or model:v7. agents.yaml lists what each agent follows, so agents talk directly and only receive what concerns them.

Threads

incident_id and reply_to link messages into one conversation per incident.

Timeouts

An unanswered Question expires. The sender then decides with what it has and logs the missing answer, so nobody waits forever.

subscriptions:
  builder:   ["pipeline:*"]
  reviewer:  ["code:*", "feature:*"]
  inspector: ["dataset:*", "feature:*", "type:question"]
  trainer:   ["dataset:*", "model:*"]
  deployer:  ["model:*", "deployment:*"]
  monitor:   ["feature:*", "model:*", "expected_change:*"]

Who owns a problem, and how conflicts are settled

Ownership

Agents ask questions upstream along the lineage map. The agent closest to the source with confirmed evidence posts a Claim. It owns the incident, tells the others what to do or not do, and writes the single card a person receives.

Conflicts

  • Safety beats progress: hold beats promote, quarantine beats retrain.
  • Fixing the cause beats patching the symptom: fix the data rather than retrain on it.
  • A deadlock or disputed claim goes to a person.

The incident card holds what happened, the root cause, the owner, actions already taken, the decision needed if any, and a link to the message thread.

    Avoiding wasted work

    If the Trainer validates a model and the Deployer rejects it, the training compute looks wasted. They check different things: the Trainer checks quality offline, the Deployer checks what only real traffic shows. To keep late rejections rare, the Deployer publishes a release contract once (for example p95 latency under 100 ms, memory under 1 GB, same input and output format as the serving API), and the Trainer runs those checks itself, cheapest first.

    1. TrainerInput and output format match the serving APIseconds
    2. TrainerModel size and memory under the limitseconds
    3. TrainerLatency benchmark on recorded traffic, in the sandboxminutes
    4. TrainerQuality overall and for every groupminutes
    5. DeployerShadow on real traffichours
    6. DeployerCanary at 5%, then 25%hours
    7. HumanApprove 100%one decision

    A rejection that still happens at shadow or 5% is cheap, and far cheaper than a bad model reaching every user. The reason goes back to the Trainer and into memory, so the next candidate avoids it. The rejected model stays in the registry in case capacity is added later. The experiments count "candidates rejected by the Deployer" next to wasted retrains; that number should fall over time.

    Shared components

    Lineage map

    A small graph that links code to features, features to datasets, datasets to model versions, and models to deployments. The Builder creates it; the Reviewer and Trainer update it. It is how a symptom in serving is traced back to a commit or a feed.

    1. commit abc123code›
    2. trip_distancefeature›
    3. 2026-03dataset›
    4. v9model›
    5. 25% canarydeployment

    Incident memory and fix selector

    A Chroma vector database. Each record holds the problem, evidence, agent, action, level, outcome and time to recover. To choose a fix: search similar past incidents, rank their fixes by success rate, let the LLM pick one or propose a new one, then store the outcome. Memory starts full of fault-injection runs where the right answer is known.

    Sandbox

    A second Docker Compose project, isolated from the real pipeline, that can replay recent batches and recorded traffic. Used for builds, feature-diff tests, repairs, training, traffic replay and confirmation replays.

    Evaluation

    Faults are injected on purpose, so the right answer is always known.

    LayerFaults
    CodeUnit change (accidental and intended), one-sided feature change, dependency bump, broken import
    DataSchema change, missing-value spike, unit change, late batch, duplicated rows
    ModelGradual and sudden drift, bad candidate, group-specific degradation
    RuntimeLatency spike, traffic surge, memory leak

    Systems compared on the same faults

    • Traditional pipeline: fixed thresholds, scheduled retraining, manual rollback
    • A single LLM agent with all the tools
    • Six agents plus a coordinator (ablation)
    • Six agents, no coordinator (this design)

    Metrics

    • Detection rate, time to detect, time to recover
    • Human alerts per incident, root-cause accuracy
    • Wasted retrains, candidates rejected by the Deployer, compute cost
    • Unsafe actions (target zero), human interventions
    • LLM calls, cost and latency; Builder success rate on 5–10 repos

    Fine-tuning

    Every LLM decision is logged next to the injected fault, so the correct decision is known. By weeks 8–9 that's a labelled dataset. A small local model is LoRA-tuned on one decision, such as the Inspector's repair-or-quarantine choice or the Reviewer's intent detection, and compared to the base LLM on accuracy, cost and speed.

    Limits and open questions

    • The Builder handles Python ML projects only and relies on templates.
    • Faults are injected, not real, so results cover known failure types.
    • LLM decisions can vary between runs; fixed JSON, action menus and logging reduce this but don't remove it.
    • Still open: local vs API LLM, the Trainer's gain threshold, the Deployer's hard limits, and the Question timeout.
